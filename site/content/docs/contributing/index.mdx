## Quickstart

You need:

- [Bun](https://bun.sh/). The required CI check pins Bun 1.4.4, so use that version or newer to match it.
- Node.js, for `bun run fresh:check` and the `ashlr-plugin` CLI.
- Git, and the [GitHub CLI](https://cli.github.com/) (`gh`) for cloning, forking, opening PRs and arming auto-merge.
- Perl 5 for the secret scan. It needs no extra modules and is preinstalled on macOS and most Linux distributions.

```sh
git clone https://github.com/ashlrai/ashlr-plugin
cd ashlr-plugin
bun install
bun run typecheck                         # bunx tsc --noEmit
bun run test                              # plugin tests
(cd server && bun install && bun test)    # server tests, own dependencies
```

The plugin and server are separate test suites with separate dependency trees. The plugin is the user-facing MCP code; the server (`server/`) is the optional Pro hosted backend. Use `bun run test` for the plugin rather than plain `bun test`: it prepares derived docs before the suite starts. `bun run check` runs every repository check; run `bun install` in `server/`, `site/` and `vscode/` first, as CI does. Each new git worktree needs its own `bun install` too.

## Agents work here too

ashlr is part of the [Ashlr ecosystem](/docs/getting-started#part-of-the-ashlr-ecosystem), where agents do the engineering and the human sits as a passive board member. Most PRs here are opened by coding agents under the rules in [AGENTS.md](https://github.com/ashlrai/ashlr-plugin/blob/main/AGENTS.md): branch, commit, open a PR, and merge on green. Two hot-file rules keep parallel PRs from colliding:

- New pipe server cases go in a new test file such as `__tests__/pipe-server-<topic>.test.ts`, not in `__tests__/pipe-server.test.ts`.
- Do not commit a regenerated `site/lib/docs.generated.json`.

Agents that want to use the plugin, not just edit it, start at [llms.txt](https://plugin.ashlr.ai/llms.txt).

## From branch to main

People and agents take the same path.

1. **Branch or fork.** With write access, branch from `main`. Without it, fork first: `gh repo fork ashlrai/ashlr-plugin --clone`.
2. **Check locally.** Commit your work, then run `bun scripts/premerge-local.ts origin/main` (in a fork whose `main` lags, use `upstream/main`). It picks the tests your committed diff affects, runs them alongside `bun run typecheck` within a 60-second budget (`--budget-ms <n>` raises it), and prints one JSON verdict. It exits 0 on `"status":"pass"` and 1 otherwise, and it fails rather than skips when it cannot select tests. See [Testing](/docs/contributing/testing#run-what-your-branch-affects). For docs-only changes, also run the doc tests listed in [AGENTS.md](https://github.com/ashlrai/ashlr-plugin/blob/main/AGENTS.md#work-in-this-repository).
3. **Scan for secrets.** `git diff origin/main...HEAD | perl .github/tests/secret-shape/scrub.pl --check --allow-fixtures` runs the same scanner CI does (in a fork, diff against `upstream/main`). It prints a count and exits 1 on a match, never the value.
4. **Open a PR** using the template. Keep it to one concern and say how you tested it. If behavior changed, add a line under `## [Unreleased]` in `CHANGELOG.md`.
5. **Arm auto-merge** with `gh pr merge --auto`. That needs write access, so a maintainer arms it for a fork PR. The PR then merges through the merge queue once `CI Gate` is green, with no manual merge step.

What the pre-merge check runs depends on what your commits change. Text docs select no tests, so it runs only the typecheck: `.md`, `.mdx`, `.rst` and `.txt` files in a `docs/` folder (including `site/content/docs/`), any README, CHANGELOG, CONTRIBUTING or LICENSE file, and top-level files such as `AGENTS.md` and `llms.txt`. That is narrower than CI's docs-only list: a `meta.json` beside the site docs, any other file under `site/` or `video/`, and anything under `.github/` (the PR template included) count as config or source and run all three suites. Markdown under `commands/`, `skills/` and `agents/` is product input, not docs. A changed test file runs just that file. A change under `servers/`, `scripts/`, `hooks/`, `ports/`, `commands/`, `skills/`, `agents/` or `__tests__/` runs all three suites (`__tests__`, `server/tests` and `integration/tests`), and so does a config file (JSON, YAML, a lockfile or a dotfile) or any other source file. A change under `server/` runs `server/tests` and `integration/tests`; one under `integration/` runs only `integration/tests`. `server/` and `integration/` have their own dependencies, so for those diffs run `(cd server && bun install) && (cd integration && bun install)` first and raise the budget, for example `--budget-ms 600000`. A fail whose step note says the budget ran out means the budget was too small, not that a test failed.

`CI Gate` is the single required check. On a PR it requires `fast checks` (version sync, plus install, typecheck and site release facts for code changes) and `Secret-shape scan`. The merge queue run always does the install, typecheck and release-facts steps, even for a docs-only PR. The full suite runs daily, and coverage, CodeQL and the benchmark also run after each merge to `main`. None of those is a required check, and a red run is fixed forward on `main`. See [Testing](/docs/contributing/testing#ci).

The rules on `main` stop there. No approving review is required, and the merge queue squash-merges each PR, so the PR title becomes the commit subject on `main`. Write it as a conventional, imperative subject such as `docs(contributing): ...` or `fix(grep): ...`. Paths listed in [`.github/CODEOWNERS`](https://github.com/ashlrai/ashlr-plugin/blob/main/.github/CODEOWNERS) (CI workflows, the secret-shape scanner, and files that make keyed, network or loopback requests) request the code owner's review automatically. Expect a closer look there, and keep such a change in its own PR.

To run the same checks before you push, one root `bun install` is enough:

```sh
bun run version:check                                    # fast checks: every manifest has the same version
bun run typecheck                                        # fast checks, code changes only
bun run site/scripts/gen-docs.ts --check --skip-corpus   # fast checks, code changes only: site release facts are fresh
git diff origin/main...HEAD | perl .github/tests/secret-shape/scrub.pl --check --allow-fixtures   # Secret-shape scan
```

If the release-facts check reports a stale file after a version, tool or command change, run `bun run site/scripts/gen-docs.ts` and commit the files it rewrites, except `site/lib/docs.generated.json`.

## Contribute from a fork with your own agent

No write access? You can still hand the whole job to Claude Code, Codex or another coding agent. Set up the fork once:

```sh
gh repo fork ashlrai/ashlr-plugin --clone   # origin = your fork, upstream = ashlrai/ashlr-plugin
cd ashlr-plugin
bun install
git fetch upstream
git switch -c fix/<topic> upstream/main   # branch from the current upstream main
```

Then give your agent a prompt like this:

> Read AGENTS.md and the "From branch to main" section of CONTRIBUTING.md, and follow them. Fix (issue link). Keep the diff to one concern, commit, run `bun scripts/premerge-local.ts upstream/main` until it reports `"status":"pass"` (if the diff touches code, install the `server/` and `integration/` dependencies and raise `--budget-ms` first), and run the secret scan on `git diff upstream/main...HEAD`. Then push the branch to my fork and open a PR against `ashlrai/ashlr-plugin` `main` using the PR template.

The steps that differ from a maintainer branch use your fork and its `upstream` remote:

```sh
git diff upstream/main...HEAD | perl .github/tests/secret-shape/scrub.pl --check --allow-fixtures   # scan against the PR's real base
git push -u origin fix/<topic>   # push to your fork
gh pr create --repo ashlrai/ashlr-plugin --base main --head <your-github-user>:fix/<topic> --fill
```

After that:

- `CI Gate` runs on the PR. For a docs-only change (`docs/`, `site/`, `video/`, top-level Markdown, `LICENSE` or issue templates), the PR run of `fast checks` skips the install, typecheck and release-facts steps, so it is mostly version sync and the secret scan. The merge queue run always does the full `fast checks`. GitHub can hold workflow runs from a first-time contributor until a maintainer approves them.
- You cannot arm auto-merge on a fork PR. A maintainer or fleet agent arms it, and the PR lands through the merge queue once `CI Gate` is green.
- In a fork, `origin/main` is your fork's `main`, which stops moving once you fork. CI compares the PR against `ashlrai/ashlr-plugin` `main`, so local checks use `upstream/main` too.
- If `main` moved on, run `git pull upstream main` on your branch and push again.

## Finding something to work on

New here? Start with the [good first issue](https://github.com/ashlrai/ashlr-plugin/labels/good%20first%20issue) label; [help wanted](https://github.com/ashlrai/ashlr-plugin/labels/help%20wanted) marks issues we would especially like a PR for. Comment on the issue before you start, keep the PR tied to one issue, and open an issue first if you are unsure something belongs here.

## What we're looking for

- **Bug fixes** with a regression test.
- **MCP tool fixes, tests and polish** in `servers/` (the catalog is `servers/_tool-catalog.json`). If you change a tool's output, the `RESULT` line of `bun run bench -- --repo . --dry-run` should not drop by more than 5 points against `main`. If you add a tool or change its name, description or input schema, run `bun run references:sync`; see [Adding a new MCP tool](/docs/contributing/architecture#adding-a-new-mcp-tool).
- **Genome retrieval and sync** in `servers/_genome-*.ts`. The genome, compression and budgeting algorithms themselves live in [`@ashlr/core-efficiency`](https://github.com/ashlrai/ashlr-core-efficiency); open those PRs there.
- **Agents, slash commands and skills** in `agents/`, `commands/` and `skills/`. Run `bun run doctor:sync` after changing skills, commands or hooks; it rewrites `.claude-plugin/install-manifest.json`.
- **Documentation**, including the pages under `site/content/docs/`. Some pages, such as the tool and command references, are generated from repository sources; [Edit the docs](https://github.com/ashlrai/ashlr-plugin/blob/main/site/README.md#edit-the-docs) lists them and what to edit instead.
- **Cross-platform fixes.** Windows CI is the toughest target; flake fixes are always welcome.

## What gets rejected

- Telemetry, analytics, or tracking that isn't strictly opt-in. The contract is [docs/telemetry.md](https://github.com/ashlrai/ashlr-plugin/blob/main/docs/telemetry.md).
- Tools that depend on closed-source services without a clean local fallback.
- Anything that breaks the [privacy commitments](/docs/pro#privacy-commitments), such as telemetry that includes paths, source, or query content.
- Bundled third-party code that requires shipping binaries.
