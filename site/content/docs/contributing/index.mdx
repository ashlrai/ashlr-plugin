## Quickstart

```sh
git clone https://github.com/ashlrai/ashlr-plugin
cd ashlr-plugin
bun install
bun run typecheck                         # bunx tsc --noEmit
bun run test                              # plugin tests
(cd server && bun install && bun test)    # server tests, own dependencies
```

The plugin and server are separate test suites with separate dependency trees. The plugin is the user-facing MCP code; the server (`server/`) is the optional Pro hosted backend. Use `bun run test` for the plugin rather than plain `bun test`: it prepares derived docs before the suite starts. `bun run check` runs every repository check; run `bun install` in `server/`, `site/` and `vscode/` first, as CI does. Each new git worktree needs its own `bun install` too.

## Agents work here too

ashlr is part of the [Ashlr ecosystem](/docs/getting-started#part-of-the-ashlr-ecosystem), where agents do the engineering and the human sits as a passive board member. Most PRs here are opened by coding agents under the rules in [AGENTS.md](https://github.com/ashlrai/ashlr-plugin/blob/main/AGENTS.md): branch, commit, open a PR, and merge on green. Two hot-file rules keep parallel PRs from colliding:

- New pipe server cases go in a new test file such as `__tests__/pipe-server-<topic>.test.ts`, not in `__tests__/pipe-server.test.ts`.
- Do not commit a regenerated `site/lib/docs.generated.json`.

Agents that want to use the plugin, not just edit it, start at [llms.txt](https://plugin.ashlr.ai/llms.txt).

## From branch to main

People and agents take the same path.

1. **Branch or fork.** With write access, branch from `main`. Without it, fork first: `gh repo fork ashlrai/ashlr-plugin --clone`.
2. **Check locally.** Run `bun run typecheck` and the tests you touched (`bun test __tests__/<file>.test.ts`). For docs-only changes, run the doc tests listed in [AGENTS.md](https://github.com/ashlrai/ashlr-plugin/blob/main/AGENTS.md#work-in-this-repository).
3. **Scan for secrets.** `git diff origin/main...HEAD | perl .github/tests/secret-shape/scrub.pl --check --allow-fixtures` runs the same scanner CI does. It prints a count and exits 1 on a match, never the value.
4. **Open a PR** using the template. Keep it to one concern and say how you tested it.
5. **Arm auto-merge** with `gh pr merge --auto`. That needs write access, so a maintainer arms it for a fork PR. The PR then merges through the merge queue once `CI Gate` is green, with no manual merge step.

`CI Gate` is the single required check. On a PR it requires `fast checks` (version sync, plus install, typecheck and site release facts for code changes) and `Secret-shape scan`. The full suite runs daily, and coverage, CodeQL and the benchmark also run after each merge to `main`. None of those is a required check, and a red run is fixed forward on `main`. See [Testing](/docs/contributing/testing#ci).

## Finding something to work on

New here? Start with the [good first issue](https://github.com/ashlrai/ashlr-plugin/labels/good%20first%20issue) label; [help wanted](https://github.com/ashlrai/ashlr-plugin/labels/help%20wanted) marks issues we would especially like a PR for. Comment on the issue before you start, keep the PR tied to one issue, and open an issue first if you are unsure something belongs here.

## What we're looking for

- **Bug fixes** with a regression test.
- **MCP tool fixes, tests and polish** in `servers/` (the catalog is `servers/_tool-catalog.json`). If you change a tool's output, the `RESULT` line of `bun run bench -- --repo . --dry-run` should not drop by more than 5 points against `main`.
- **Genome retrieval and sync** in `servers/_genome-*.ts`. The genome, compression and budgeting algorithms themselves live in [`@ashlr/core-efficiency`](https://github.com/ashlrai/ashlr-core-efficiency); open those PRs there.
- **Agents, slash commands and skills** in `agents/`, `commands/` and `skills/`. Run `bun run doctor:sync` after changing skills, commands or hooks.
- **Documentation**, including the tool pages under `site/content/docs/tools/`.
- **Cross-platform fixes.** Windows CI is the toughest target; flake fixes are always welcome.

## What gets rejected

- Telemetry, analytics, or tracking that isn't strictly opt-in. The contract is [docs/telemetry.md](https://github.com/ashlrai/ashlr-plugin/blob/main/docs/telemetry.md).
- Tools that depend on closed-source services without a clean local fallback.
- Anything that breaks the [privacy commitments](/docs/pro#privacy-commitments), such as telemetry that includes paths, source, or query content.
- Bundled third-party code that requires shipping binaries.
